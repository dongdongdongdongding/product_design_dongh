# 디자인 방향 — 시안 비교로 정하기

목적: 사용자가 글 설명이 아니라 **실제 화면을 보고** 방향을 고르게 하는 것. 질문은 그림으로 답할 수 없는 것만 한다. 품질 기준은 `design-system` 스킬(레퍼런스 · HIG · 휴리스틱 · 밀도)을 함께 연다.

## 1. 근거 모으기 (묻기 전에)

- 원본 자료 · 운영 사이트 · 참고 화면설계서 · 디자인 가이드에서 정해진 것을 먼저 읽는다. 운영 사이트가 있으면 `source-intake` 3절로 색 · 글꼴 · 카드 · 버튼 · 입력 높이를 잰다(가장 강한 근거).
- **외부 레퍼런스를 직접 찾는다** — `design-system/references/reference-research.md`. 같은 업무의 서비스 · 공개 디자인 시스템 · 패턴 사례 5~10건을 `research/레퍼런스.md`에 정리하고, 같은 문제를 다르게 푼 방식을 시안 축으로 삼는다.

## 2. 꼭 필요한 것만 묻기 (0~4개)

그림으로 고를 수 있는 것(톤 · 밀도 · 메뉴 위치 · 목록 모양 · 등록 방식)은 묻지 않고 시안으로 보여 준다. 묻는 것은 그림으로 알 수 없는 것뿐이다:
- 브랜드 색 · 로고 · 글꼴 지정이 있나 (운영 사이트 · 가이드에서 못 찾았을 때)
- 반드시 따라야 할 기준(기관 디자인 시스템 · 접근성 수준 · 다크 모드)
- 시안을 그릴 핵심 화면 (기본: 사용자가 가장 오래 머무는 화면 — 보통 주 목록 또는 대시보드)

선택형 질문 도구가 있으면 쓰고, 없으면 번호 목록. 모두 기본값을 붙인다. 답을 기다리지 않아도 되면(근거가 충분하면) 묻지 않고 바로 시안을 그린다. 질문 목록 전체는 `references/design-questions.md`(브리프 칸을 채울 때 참고).

## 3. 시안 2~4개 그리기

- **한 화면, 다른 방향.** 시안끼리는 의미 있는 축 1~2개가 달라야 한다(색만 다른 시안은 시안이 아니다). 축 예: 정보 밀도(넉넉 / 촘촘), 배치(목록 중심 / 지도 · 시각 중심 / 분할 패널), 탐색(사이드바 / 상단), 편집 방식(페이지 / 오른쪽 패널 / 팝업), 톤(담백 업무형 / iOS형 정제 / 공공형 고밀도). 운영 사이트가 있으면 시안 A는 **운영 사이트 그대로의 톤**으로 둔다.
- **시안도 기획 밀도를 지킨다**(`design-system/references/planning-bar.md`): 실제 업무 데이터 6~10행, 필터 · 건수 · 상태 배지 · 작업 버튼 · 빈 칸 없음. 시안이 허접하면 고를 수가 없다.
- **쓰는 곳**: `spec-kit/variants.js` (양식 `templates/design/variants.js`). project.js와 같은 범위라 `shell` · `card` · `field` 같은 시안 도구를 그대로 쓰고, 시안별 스타일은 `css`에 `.v-A .scr …`처럼 범위를 붙인다.
- 각 시안에 이름 · 한 줄 설명 · 근거(레퍼런스 번호 · HIG 원칙)를 단다.

## 4. Claude Design 캔버스로 보여 주기

```bash
node scripts/export_design.mjs <spec-kit> <spec-kit>/design --variants-only   # 화면이 아직 없을 때. 있으면 옵션 없이
```
- 게시: `design-canvas` 스킬 3절 — Design 타입 Artifact를 새로 만들어 `V-A.dc.html` … 를 올린다. **이 Artifact가 프로젝트의 디자인 캔버스가 되고, 이후 초안 · 전체 화면도 같은 URL에 쌓는다.** URL을 `progress.md`에 적는다.
- Design 타입이 없는 환경(Codex · 기타): `templates/design/harness.html`을 `design/`에 복사하고 로컬 서버로 `harness.html?boards=V-A,V-B,V-C`를 열어 나란히 보여 준다. 캡처 도구가 있으면 캡처도 함께.
- 보여 줄 때 한 화면에 요약:

```
시안 3개를 캔버스에 올렸습니다: <링크>
  A 운영 사이트 톤 그대로 — 표 중심, 행 40px (근거: 운영 사이트 측정)
  B 정제형 — 8px 격자, 카드 반경 12, 주 색 면적 최소 (근거: HIG 위계 · 레퍼런스 ②)
  C 분할 패널 — 목록 + 오른쪽 상세, 촘촘한 표 (근거: 레퍼런스 ④⑥)
고르거나 섞어 말해 주세요(예: "B로, 표 밀도는 C"). 캔버스에서 직접 고쳐도 됩니다 — 고쳤다고 말하면 가져옵니다.
```

## 5. 고른 것 → 브리프 · 토큰

- 캔버스에서 고쳤다고 하면: `Artifact read`(paths)로 최신 보드를 받아 `node scripts/import_design.mjs <받은 폴더> <spec-kit>`로 무엇이 바뀌었는지 보고, 시안 보드(V-*)의 변경은 직접 읽어 반영한다.
- 고른 시안(섞은 경우 섞은 결과)을 기준으로:
  1. `research/디자인브리프.md`(양식 `templates/intake/디자인브리프.md`) — 근거 칸에 "시안 B 선택 + C의 표 밀도".
  2. `design-system/tokens.json`(시작: `templates/design-system/tokens.json`) → `python -I scripts/design_tokens.py css` · `link` · `check`. 대비 미달은 고치고 알린다.
  3. theme.css 본문을 고른 시안의 값으로(클래스 이름은 유지).
- 섞은 결과를 한 번 더 그려 보여 줄지는 차이가 클 때만. 작으면 초안에 바로 반영하고 "초안에서 보시고 바꾸셔도 됩니다".
- `progress.md`의 디자인 방향 칸에 고른 시안 · 브리프 · 캔버스 URL을 적는다.

## 원칙

- 운영 사이트의 실제 값 > 사용자가 준 디자인 가이드 > 사용자 선택 > 플랫폼 원칙 > 레퍼런스 > 기본값. 충돌하면 어느 쪽인지 한 번만 묻는다.
- 시안을 고른 뒤에도 초안 단계에서 얼마든지 바뀐다. 처음부터 완벽하게 맞추려고 질문을 늘리지 않는다.
- 시안을 그린 뒤 `design-system` 휴리스틱 · HIG 점검 질문으로 스스로 한 번 보고, 심각도 3 이상은 고친 다음 보여 준다.

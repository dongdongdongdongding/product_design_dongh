# 화면 설계 산출물 키트 — 안내 흐름

사용자는 기획자 · PM · 디자이너일 수 있다. 명령어나 파일 구조를 몰라도 되게, **지금 어느 단계인지 · 무엇을 받아야 하는지 · 다음에 무엇이 나오는지**를 매번 짧게 알려 주며 진행한다.

플러그인 루트: 이 파일 기준 `../../`. (설치 스크립트로 스킬만 복사했다면 파일 맨 아래 `KIT_ROOT:` 줄의 경로) 모든 하위 스킬에 적힌 `templates/` · `scripts/` · `engine/` 경로는 이 루트 기준이다.
- `engine/` 공통 엔진 — 프로젝트마다 고치지 않는다.
- `templates/project-starter/` 새 프로젝트 틀, `templates/intake/` 진행 기록 · 자료 요청 · 디자인 브리프 양식.
- `examples/demo-park/` 끝까지 만든 가상 예시. 처음이면 이것을 보여 주며 "이런 결과가 나옵니다"라고 설명해도 좋다.
- `scripts/` build_kit.py · check_docs.py · export_design.mjs · audits/*.js.

## 단계 지도

| 단계 | 하는 일 | 사용자에게 받는 것 · 확인 | 결과 | 스킬 |
|---|---|---|---|---|
| 0. 시작 | 지금 가진 것을 보고 시작 지점을 정한다 | "무엇을 갖고 계세요?" | `spec-kit/progress.md` | (이 스킬) |
| 1. 자료 받기 | 기획서 · 요구사항 정의서를 읽고 요구 목록을 만든다 | 파일 · 링크, **요구 목록 확인** | `research/근거노트.md` | `source-intake` |
| 2. 디자인 질문 | 톤 · 기준 사이트 · 화면 밀도 · 컴포넌트 등을 묻는다 | 질문 답(기본값 허용), **브리프 확인** | `research/디자인브리프.md`, `theme.css` | `design-brief` |
| 3. 초안 | 핵심 화면 2~4개 + 문서 뼈대 + 플로우 맵 초안을 만들어 보여 준다 | — | `flowmap.html`(초안) | `draft-review` |
| 4. 검토 · 개선 | 피드백을 받아 고치고 다시 보여 준다(반복) | 유지 / 고칠 것 / 추가할 것, **방향 승인** | 검토 이슈 · 변경 이력 | `draft-review` |
| 5. 전체 확장 | 모든 화면 · 문서 3종 · 연결을 채운 플로우 맵 | 범위 · 공수 결정 | `docs/` 3종, 플로우 맵 | `spec-docs` · `flowmap-artifact` |
| 6. 화면설계서 · 디자인 | SB 탭, (선택) Claude Design 보드 | 참고 SB 형식 | `sb-pages.js`, `design/` | `sb-screen-spec` · `design-canvas` |
| 7. 검수 · 전달 | 자동 검수 0건 → 게시 또는 파일 전달 | 게시 여부 | 링크 · 파일 | `artifact-qa` |

**굵은 글씨**가 확인 지점이다. 확인 지점에서는 결과를 짧게 보여 주고 "이대로 갈까요, 고칠 것이 있나요?"를 묻는다.

## 작업 폴더

결과물은 키트 저장소가 아니라 사용자의 **작업 폴더**에 만든다. 구조는 항상 같다:
```
<작업 폴더>/
  research/근거노트.md · 디자인브리프.md   ← 1 · 2단계
  spec-kit/progress.md                      ← 진행 기록
  spec-kit/kit.json · theme.css · project.js · sb-pages.js · docs/ · flowmap.html · design/
```
- 사용자가 폴더를 말하면 그곳, 아니면 현재 폴더. 단, 현재 폴더가 키트 저장소 자체(`engine/`이 있는 곳)면 "결과물을 어디에 만들까요? 기본: `../<프로젝트명>-spec`"을 0단계 질문에 함께 묻는다.
- 사용자 저장소에 이미 `docs/`가 있으면 `kit.json`의 `docs`가 그곳을 가리키게 해도 된다.

## 0. 시작 — 시작 지점 정하기

**첫 메시지 형식**(어떤 에이전트든 같게): ① 무엇을 만들어 주는지 한 줄 ② 단계 지도 7줄(단계명 · 결과물만) ③ 아래 질문. 길게 설명하지 않는다.

1. 작업 폴더에 `spec-kit/progress.md`가 있으면 읽고 "지난번 ○단계까지 했습니다. 이어서 ○○를 할까요?"로 시작한다.
2. 없으면 한 번에 묻는다(모르면 "없음"이라고 해도 된다고 알린다. 답하지 않은 항목은 "없음"으로 보고 가정 목록에 적는다):
   - 기획서가 있나요? 있으면 파일 경로나 첨부로 주세요. (PPT · PDF · HWP · 노션 · 이미지)
   - 요구사항 정의서나 요청서(RFP · 과업지시서)가 있나요? 있으면 경로 · 첨부로.
   - 지금 운영 중인 사이트(관리자 화면) 주소가 있나요?
   - 따라야 할 화면설계서 · 디자인 가이드 예시가 있나요?
   - 이번 결과물의 용도는? (실제 개발 문서 / 제안 · 시연 / 내부 검토)
3. 가진 것에 따라 시작 단계를 정하고 알린다:

| 가진 것 | 시작 |
|---|---|
| 자료만 있음 | 1단계 |
| 기능정의서 · 상세명세가 이미 있음 | 1단계는 요구 목록만 뽑고 2단계로 |
| 화면 시안 · 캡처가 있음 | 2단계 질문을 줄이고(시안에서 읽음) 3단계로 |
| 이미 만든 spec-kit 폴더 | 원하는 단계로 바로 (예: "SB만 다시", "연결선만 고쳐") |
| 아무것도 없음 · 아이디어만 | 한두 문장 설명을 받아 요구 목록 초안을 같이 만든다(전부 "가정" 표시) |

자료 종류는 이름 · 확장자가 아니라 **내용**으로 판단한다: 요구 ID · 필수/선택 표가 있으면 요구사항 정의서, 화면 그림 · 배치가 있으면 기획서, 기능 ID · 예외 · 검수 표가 있으면 이미 만든 개발 문서. 섞여 있으면 그렇다고 알리고 각각 쓴다.

4. `templates/intake/progress.md`를 `spec-kit/progress.md`로 복사하고 시작 단계 · 받은 자료를 적는다. 폴더 틀은 `templates/project-starter`를 `spec-kit/`으로 복사한다(이미 있으면 덮어쓰지 않는다).

## 진행 규칙 — 체계적이되 자유롭게

- **매 단계 머리말**: "〔2/7 디자인 질문〕 화면 톤을 정합니다. 질문 6개, 모르면 '기본값'이라고 답하세요."처럼 단계 번호 · 목적 · 할 일을 한 줄로.
- **매 단계 꼬리말**: 만든 것(파일 · 숫자) → 확인 질문 → "다음은 ○단계: ○○" 예고.
- **건너뛰기 · 되돌아가기 허용**: 사용자가 순서를 바꾸면 따른다. 앞 단계 결과가 없으면 최소 가정으로 채우고 `progress.md`의 "가정" 목록과 화면 검토 이슈(`st: 'ask'`)에 남긴다. 뒤에서 앞 단계를 고치면(예: 4단계에서 요구 추가) 영향받는 산출물을 알려 주고 다시 만든다.
- **"기본값" · "좋아요" 답**: 그 단계의 확인 지점을 통과한 것으로 보고, 결과 요약만 보여 준 뒤 다음 단계를 바로 진행한다(다시 묻지 않는다).
- **자동 모드**: "알아서 끝까지", "질문 말고 진행"이라고 하면 확인 지점에서 멈추지 않고 기본값으로 7단계까지 간 뒤, 마지막에 가정 · 기본값 목록을 한 번에 보여 주고 고칠 것을 묻는다.
- **질문 방식**: 한 번에 최대 7개(넘으면 두 번에 나누되, 두 번째 묶음은 기본값을 먼저 보여 주고 "바꿀 것만" 묻는다), 항목마다 기본값을 붙인다. 선택형 질문 도구(AskUserQuestion 등)가 있으면 쓰고(한 번에 4개까지), 없으면 번호 목록으로 묻는다. 기본값이 분명한 것은 묻지 않고 정한 뒤 알린다.
- **진행 기록**: 단계가 끝날 때마다 `progress.md`의 체크 · 결정 · 미결 · 피드백 회차를 갱신한다. 대화가 끊겨도 이 파일로 이어 간다.

## 원칙

- **근거 우선**: 원본 자료와 운영 사이트에서 확인한 사실로 쓴다. 확인 못 한 것은 "확인 필요"로 표시한다. 로그인이 필요한 사이트는 사용자가 직접 로그인한다(비밀번호를 대신 입력하지 않는다).
- **기존 사이트와 같은 톤**: 운영 사이트가 있으면 거기서 잰 값으로 그린다. 기획 PPT는 항목 · 배치 근거로 쓴다. 운영 사이트가 없으면 2단계 브리프를 따른다.
- **요구 충족은 화면 단위로**: 요구가 기능 ID에 연결됐는지뿐 아니라 그 입력 · 동작이 어느 화면 어디에 있는지 확인한다.
- **한 원본, 여러 산출물**: 시안은 `project.js` 한 곳에 쓰고 플로우 맵 · SB · 디자인 캔버스가 모두 그것을 쓴다. 초안도 같은 파일로 만들어 확장하므로 버리는 작업이 없다.
- **용도에 맞게**: 실제 개발 문서면 화면에 시연 · 예시 배지 · 안내 문구를 넣지 않는다.

|---|---|---|

## 자주 틀린 것

- 문자열 일괄 치환은 다른 화면의 같은 문자열까지 바꾼다. 치환 전 개수를 세고(`count == 1`) 문맥을 붙인다.
- 링크 공유 중인 Artifact는 게시하면 보는 사람에게 즉시 바뀐다. 게시가 거절되면 최신본을 읽어 병합한 뒤 게시한다.
- 자동 검수는 `python -m http.server --bind 127.0.0.1`로 연 페이지에서만 돈다(file:// 은 브라우저 확장이 못 연다).
- 다운로드한 런타임 · 외부 스크립트는 실행하지 않는다.
- 기능 · 예외 · 검수를 추가하면 kit.json의 `expect`와 문서 변경 이력도 함께 고친다.

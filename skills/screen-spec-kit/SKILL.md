# 화면 설계 산출물 키트

사용자는 기획자 · PM · 디자이너다. 이 키트는 **사용자가 준 것이 무엇이든(자료 묶음이든 아이디어 한 줄이든) 서비스 전체를 개발 가능한 단위까지 해석해 그림과 문서로 내놓는 것**이 일이다. 사용자에게 기획을 떠넘기는 질문("어떤 메뉴가 필요하세요?")을 하지 않는다. 먼저 해석해 보여 주고, 갈리는 곳만 기본안과 함께 묻는다.

플러그인 루트: 이 파일 기준 `../../`. (설치 스크립트로 스킬만 복사했다면 파일 맨 아래 `KIT_ROOT:` 줄의 경로) 모든 하위 스킬에 적힌 `templates/` · `scripts/` · `engine/` 경로는 이 루트 기준이다.
- `engine/` 공통 엔진 — 프로젝트마다 고치지 않는다.
- `templates/project-starter/` 새 프로젝트 틀, `templates/intake/` 진행 기록 · 자료 요청 · 기획 분해 · 디자인 브리프 양식, `templates/design/` 시안 · 캔버스 점검, `templates/design-system/` 토큰 · 컴포넌트.
- `examples/demo-park/` 끝까지 만든 가상 예시.
- `scripts/` build_kit.py · check_docs.py · check_density.mjs · export_design.mjs · import_design.mjs · design_tokens.py · audits/*.js.

## 일하는 방식 — 단계 강제가 아니라 하나의 세션

아래 작업은 **순서가 아니라 메뉴**다. 사용자가 원하는 것부터, 원하는 것만 한다("SB만 다시", "디자인 시안만", "아이디어 분해만"). 앞 작업 결과가 없으면 막지 않고 최소 가정으로 채운 뒤 가정이라고 표시한다. 아무 말 없이 "시작"이면 위에서부터 이어서 진행하되, 사용자 결정이 필요한 곳에서만 멈춘다.

| 작업 | 하는 일 | 결과 | 스킬 |
|---|---|---|---|
| 자료 읽기 | 기획서 · 요구사항 정의서 · 운영 사이트를 읽고 요구 목록(원본 ID 유지) | `research/근거노트.md` | `source-intake` |
| 기획 분해 | 역할 → 메뉴 → 화면 → 기능 → 컴포넌트 · 동작 → 연결 → 데이터 · 상태 · 권한 → 예외 → 기본 결정 | `research/기획분해.md` | `plan-decompose` |
| 디자인 방향 | 외부 레퍼런스 조사 → 핵심 화면 하나를 시안 2~4개로 → 캔버스에서 고르기 · 고치기 → 브리프 · 토큰 | 디자인 캔버스(V-*), `research/디자인브리프.md`, `design-system/tokens.json` | `design-brief` · `design-system` |
| 초안 · 검토 | 핵심 화면 2~4개를 밀도 있게 → 캔버스 + 플로우 맵 → 캔버스 수정 · 말 피드백 반영 반복 | 디자인 캔버스, `flowmap.html` | `draft-review` · `design-canvas` |
| 전체 확장 | 나머지 화면 · 문서 3종 · 연결 | `docs/` 3종, 플로우 맵 | `spec-docs` · `flowmap-artifact` |
| 화면설계서 · 디자인 시스템 | SB 탭, 토큰 · 컴포넌트 보드, 캔버스 다듬기 | `sb-pages.js`, DS 보드 | `sb-screen-spec` · `design-system` · `design-canvas` |
| 검수 · 전달 | 문서 정합 · 밀도 · 자동 검수 0건 → 게시 · 파일 | 링크 · 파일 | `artifact-qa` |

**사용자가 결정해야 해서 멈추는 곳**은 셋뿐이다: 기획 분해의 "확인 필요"(기본안으로 진행하며 답을 기다림), 시안 고르기, 범위 · 공수가 늘어나는 변경. 나머지는 진행하고 결과로 보여 준다. "알아서 끝까지"라고 하면 이것도 기본안으로 진행하고 마지막에 한 번에 묻는다.

**현황 줄**: 응답 끝에 현황을 한 줄로 붙인다(게이트가 아니라 칩). 예: `현황 — 자료 ✓ · 분해 ✓(화면 14) · 디자인 B안 · 초안 2회차 · 문서 · SB · 검수 —` 그리고 "다음 추천: ○○" 한 줄. 사용자가 다른 것을 하자고 하면 그쪽으로 간다.

## 첫 응답

1. 작업 폴더에 `spec-kit/progress.md`가 있으면 읽고 "지난번 ○○까지 했습니다. 이어서 ○○를 할까요, 다른 것을 할까요?"
2. 없으면 짧게: 무엇을 만들어 주는지 한 줄 + 위 작업 표 이름만 한 줄씩 + "가진 것을 주세요 — 기획서 · 요구사항 정의서 · 운영 사이트 주소 · 참고 화면설계서, 또는 아이디어 한두 문장이면 됩니다. 용도(개발 문서 / 제안 · 시연 / 내부 검토)도 알려 주시면 좋습니다(기본: 개발 문서)."
3. 받은 것이 있으면 묻지 말고 바로 읽고 분해를 시작한다. 자료 종류는 이름이 아니라 내용으로 판단한다: 요구 ID · 필수/선택 표 → 요구사항 정의서, 화면 그림 · 배치 → 기획서, 기능 ID · 예외 · 검수 표 → 이미 만든 개발 문서, 문장 몇 줄 → 아이디어.
4. `templates/intake/progress.md`를 `spec-kit/progress.md`로, `templates/project-starter`를 `spec-kit/`으로 복사한다(이미 있으면 덮어쓰지 않는다).

## 작업 폴더

결과물은 키트 저장소가 아니라 사용자의 **작업 폴더**에 만든다:
```
<작업 폴더>/
  research/근거노트.md · 기획분해.md · 레퍼런스.md · 디자인브리프.md · 휴리스틱.md
  spec-kit/progress.md · kit.json · theme.css · project.js · variants.js · sb-pages.js
  spec-kit/docs/ · design-system/ · design-import/ · design/ · flowmap.html
```
- 사용자가 폴더를 말하면 그곳, 아니면 현재 폴더. 현재 폴더가 키트 저장소 자체(`engine/`이 있는 곳)면 기본 `../<프로젝트명>-spec`에 만들고 알린다.
- 사용자 저장소에 이미 `docs/`가 있으면 `kit.json`의 `docs`가 그곳을 가리키게 해도 된다.

## 품질 기준

- **기획은 끝까지 분해한다**(`plan-decompose`): 원본 요구가 어느 화면 어디의 어떤 컴포넌트 · 동작으로 처리되는지까지. 동작마다 성공 · 검증 실패 · 서버 실패 · 권한 없음.
- **허접한 초안 금지**(`design-system/references/planning-bar.md`): 화면마다 실제 업무 데이터 · 필터 · 상태 · 규칙 · 예외. `check_density.mjs` 미달 0이 하한이다.
- **디자인은 그림으로 정한다**: 글로 톤을 묻지 않고 시안을 나란히 보여 준다. 레퍼런스는 직접 찾는다.
- **편집 가능한 디자인**: 시안 · 초안 · 전체 화면은 Claude Design 캔버스로 준다. 사용자가 캔버스에서 고친 것은 `import_design.mjs`로 가져와 문서 · 플로우 맵 · SB에 반영한다.
- **본 것으로 보고한다**: 화면이 좋아졌다는 말은 다시 렌더한 화면을 본 뒤에. 지표는 회귀 방지용이다.
- **규칙을 고친다**: 한 화면 땜질보다 시안 도구 · 토큰 · 컴포넌트를 고쳐 모든 화면에 함께 걸리게.
- **근거 우선**: 원본 자료와 운영 사이트에서 확인한 사실로 쓴다. 확인 못 한 것은 "확인 필요". 로그인이 필요한 사이트는 사용자가 직접 로그인한다(비밀번호를 대신 입력하지 않는다).
- **한 원본, 여러 산출물**: 시안은 `project.js`(캔버스에서 가져온 화면은 `design-import/`) 한 곳에 있고 플로우 맵 · SB · 캔버스가 모두 그것을 쓴다.
- **용도에 맞게**: 실제 개발 문서면 화면에 시연 · 예시 배지 · 안내 문구를 넣지 않는다.
- 사용자 지시가 이 기준과 어긋나면 어긋난다는 것만 한 줄로 알리고 지시대로 한다. 기준은 하한이지 상한이 아니다.

## 질문 방식

- 묻기 전에 찾는다(자료 · 운영 사이트 · 레퍼런스). 그림으로 고를 수 있는 것은 그림으로.
- 묻는다면 한 번에 최대 4개, 항목마다 기본안. 선택형 질문 도구가 있으면 쓰고(시안 미리보기를 붙일 수 있으면 붙인다), 없으면 번호 목록. 답을 기다리는 동안 기본안으로 진행할 수 있으면 진행한다.
- "기본값" · "좋아요"는 그 결정을 기본안으로 확정한 것으로 보고 다시 묻지 않는다.
- 진행 기록: 결정 · 가정 · 미결 · 피드백 회차 · 캔버스 URL을 `progress.md`에 갱신한다. 대화가 끊겨도 이 파일로 이어 간다.

## 자주 틀린 것

- 문자열 일괄 치환은 다른 화면의 같은 문자열까지 바꾼다. 치환 전 개수를 세고(`count == 1`) 문맥을 붙인다.
- 링크 공유 중인 Artifact는 게시하면 보는 사람에게 즉시 바뀐다. 게시가 거절되면 최신본을 읽어 병합한 뒤 게시한다. 디자인 캔버스는 사용자가 고쳤을 수 있으니 특히 먼저 가져온다.
- 자동 검수는 `python -m http.server --bind 127.0.0.1`로 연 페이지에서만 돈다(file:// 은 브라우저 확장이 못 연다).
- 다운로드한 런타임 · 외부 스크립트는 실행하지 않는다.
- 기능 · 예외 · 검수를 추가하면 kit.json의 `expect`와 문서 변경 이력도 함께 고친다.

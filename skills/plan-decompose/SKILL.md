# 기획 분해 — 아이디어를 메뉴 · 기능 · 컴포넌트 · 동작 · 연결로

사용자가 준 것이 한 줄 아이디어든 100쪽 요청서든, **화면을 그리기 전에 서비스 전체를 개발 가능한 단위까지 분해해 해석하는 것은 이 키트가 한다.** 사용자에게 "메뉴는 어떻게 할까요?", "어떤 기능이 필요하세요?"를 묻지 않는다. 먼저 분해한 결과를 보여 주고, 해석이 갈리는 곳만 기본안과 함께 확인받는다.

결과는 `research/기획분해.md` 한 장(양식 `templates/intake/기획분해.md`)이고, 그대로 기능정의서 · 상세명세 · `project.js`의 원본이 된다.

## 분해 순서 (위에서 아래로, 빠짐없이)

| # | 층 | 뽑는 것 | 어디로 가나 |
|---|---|---|---|
| 1 | 목적 · 범위 | 이 서비스가 줄이는 일, 이번 범위 / 제외 범위, 구현 구분(E 기존 · U UI · D 고정 데이터 · C 조건부 · F 후속) | 기능정의서 1 · 4 · 7장 |
| 2 | 사용자 · 역할 | 누가 쓰나(관리자 · 담당자 · 열람자 · 시민 …), 역할마다 주 업무 3~5개, 사용 빈도 · 환경(PC · 모바일 · 현장) | 권한 표, 화면 밀도 |
| 3 | 업무 흐름 | 역할별 주 업무를 시작 → 끝 단계로(예: 신청 → 검토 → 승인/반려 → 알림). 단계마다 입력 · 판단 · 결과 | 여정(SB journeys), FLOWS |
| 4 | 메뉴 트리 | 2단계까지, menuCode(M10 · M20 …), 메뉴마다 화면, 신규 · 기존 표시 | 기능정의서 5장 메뉴표, NAV |
| 5 | 화면 목록 | SCR-ID, 이름, 형태(페이지 · 탭 · 팝업 · 패널 · 오버레이 · 공통 상태), 진입 경로, 기능 ID | 5.1 화면 목록, SCREENS |
| 6 | 기능 | 기능 ID(`접두어-NN`, 메뉴 단위 접두어), 기능 이름, 화면, 구현 구분, **완료 기준**(검수 가능한 한 문장) | 6장 기능 목록 |
| 7 | 화면별 컴포넌트 · 동작 | 화면마다 구성 요소 표: 컴포넌트 · 내용(열 · 필드 · 값) · 동작(클릭 · 입력 · 선택 · 끌기) → 결과(상태 변화 · 메시지 · 이동 · 저장) · 데이터 | SCREENS parts/rules, H 시안, SB 마커 |
| 8 | 화면 연결 | 출발 화면 · 트리거(버튼 · 행 · 카드 · 핀) → 도착 화면 · 넘기는 값 · 돌아올 때 상태 | data-go, transData, 화면 흐름 |
| 9 | 데이터 · 상태 | 객체(필드 · 타입 · 필수 · 검증 · 기본값), 상태값과 전이 규칙(누가 · 언제 · 되돌릴 수 있나), 계산 규칙 | 상세명세 2 · 12장 |
| 10 | 권한 | 역할 × 화면 · 동작 (조회 · 등록 · 수정 · 삭제 · 승인), 권한 없을 때 보이는 모습 | 권한 표, 공통 상태 |
| 11 | 예외 후보 | 화면 · 동작마다: 입력 오류 · 빈 상태 · 조회 실패 · 저장 실패 · 권한 없음 · 동시 수정 · 이탈 · 대량 처리 일부 실패 · 외부 연동 실패 | 8장 예외 EX, 10장 검수 AT |
| 12 | 기본 결정 · 미결 | 원본이 말하지 않은 것에 대한 기본안과 이유, 확인이 필요한 것 | 8장 기본 결정, ISSUES(RV) |

## 해석 규칙

- **아이디어만 있을 때**: 같은 종류 서비스의 표준 구성으로 빈칸을 채운다 — 외부 레퍼런스를 찾아(`design-system/references/reference-research.md`) 그 업무에서 보통 있는 메뉴 · 상태 · 예외를 가져온다. 채운 것은 모두 근거 칸에 "가정(표준 구성)" 또는 "레퍼런스 ③"으로 적는다.
- **관리 대상(명사)마다 최소 세트**를 확인한다: 목록(검색 · 필터 · 정렬 · 건수 · 페이지) · 상세 · 등록 · 수정 · 상태 변경 · 삭제(또는 사용 안 함) · 이력. 빠뜨리면 "왜 없나"를 기본 결정에 적는다.
- **상태가 있는 대상**은 상태 전이표를 만든다(상태 · 다음 상태 · 누가 · 조건 · 되돌림). 버튼 · 배지 · 예외가 여기서 나온다.
- **동작마다 결과 4가지**를 적는다: 성공(메시지 · 이동), 검증 실패, 서버 실패, 권한 없음. 이것이 예외 · 검수의 재료다.
- **화면 연결은 양방향**으로 본다: 가는 길과 돌아오는 길(목록 위치 · 필터 유지, 새로고침).
- **화면 하나에 주 작업 하나.** 한 화면에 주 작업이 둘이면 탭 · 패널 · 별도 화면으로 나눈다.
- 원본이 있는 요구는 원본 ID(`SFR-001` 등)를 그대로 쓰고 기능 ID와 잇는다. 원본 요구가 어느 화면 어디에 있는지까지 내려가지 않으면 분해가 끝난 게 아니다.
- 규칙은 내용(데이터 유무 · 개수 · 상태 수)으로 정하고 특정 프로젝트의 낱말에 맞춘 예외를 만들지 않는다.

## 보여 주기

분해가 끝나면 한 화면 요약 + 파일 링크:

```
기획 분해 — research/기획분해.md
  역할 3 (관리자 · 담당자 · 열람자) · 업무 흐름 4 · 메뉴 5 (신규 3) · 화면 14 (페이지 9 · 팝업 3 · 패널 1 · 공통 상태 1)
  기능 31 · 상태 전이 2종 · 예외 후보 46 · 화면 연결 27
  가정으로 채운 것 9 (표준 구성 6 · 레퍼런스 3) · 확인 필요 3:
    1. 반려 후 재신청을 허용하나요? 기본안: 허용(새 예약 번호)
    2. …
다음: 핵심 화면 하나로 시안 3개를 그려 디자인 방향을 정합니다(바로 진행).
```
확인 필요 항목은 기본안으로 진행하고, 답이 오면 바꾼다(되돌리기 쉬운 것은 기다리지 않는다).

## 다음으로

- 분해표 → `spec-docs`(기능정의서 · 상세명세 · WBS)와 `project.js`(NAV · SCREENS · FLOWS · transData · ISSUES)로 옮긴다. 화면 ID · 기능 ID는 바꾸지 않고 그대로.
- 시안 비교는 분해표의 "가장 오래 머무는 화면"으로(`design-brief`), 초안은 분해표의 핵심 흐름 앞뒤 화면으로(`draft-review`).
- 검토 중 범위가 바뀌면 분해표를 먼저 고치고 문서 · 시안에 내린다.

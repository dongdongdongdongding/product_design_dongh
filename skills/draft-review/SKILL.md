# 초안 → 검토 · 개선 → 확장

초안도 `project.js` · `docs/`에 쓰고 같은 엔진으로 빌드한다. 승인된 초안은 그대로 전체 버전의 일부가 된다. 화면 품질 기준은 `design-system` 스킬을 함께 연다.

## 초안 만들기

1. **고르기** — 요구 목록에서 사용자가 가장 오래 머무는 화면, 입력이 가장 많은 화면, 처음 보는 패턴(지도 · 승인 흐름 등)을 2~4개. 한 흐름의 앞뒤(목록 → 상세)는 함께 고른다. 고른 이유와 **아직 안 그린 화면 목록**을 함께 알린다. 사용자가 지정하면 그것을 그린다. 시안 비교에서 고른 화면은 고른 시안을 출발점으로 쓴다.
2. **문서 뼈대** — `docs/` 3종에 변경 이력, 화면 목록(5.1), 요구 추적표(5.2), 고른 화면의 기능 · 예외 · 검수 표. `check_docs.py`가 통과해야 한다.
3. **시안 — 초안이라도 허접하지 않게** (`design-system/references/planning-bar.md`):
   - 화면마다 실제 업무 데이터 6~10행, 필터 · 건수 · 정렬 · 페이지, 상태 배지, 작업 버튼, 보조 정보(최근 이력 · 안내 · 요약 수치).
   - SCREENS에 parts · states · rules · ex · at를 채운다. 빈 상태 · 오류 · 권한 · 저장 실패 같은 상태는 공통 상태 화면이나 각 화면 states에.
   - 버튼에 `data-go`를 달아 초안끼리 연결한다. 아직 없는 화면으로 가는 버튼은 `data-go`를 달지 않고 `ISSUES`에 "미정 화면" 이슈(`st: 'ask'`)로 남긴다.
4. **스스로 점검** — 보여 주기 전에:
   - `node scripts/check_density.mjs <spec-kit>` 미달 0 (미달이면 빠진 기획을 채운다. 숫자를 맞추려고 의미 없는 요소를 넣지 않는다)
   - 휴리스틱(`design-system/references/heuristics.md`) · HIG 점검 질문 — 심각도 3 이상 고침
   - `python -I scripts/design_tokens.py check <spec-kit>` (토큰이 있을 때)
   - 렌더한 화면을 직접 본다(캡처 · harness). 본 뒤에만 "좋아졌다"고 말한다.
5. **보여 주기 — 디자인 캔버스와 플로우 맵 둘 다**:
   - `node scripts/export_design.mjs <spec-kit> <spec-kit>/design` → 시안 비교 때 만든 **같은 디자인 Artifact URL**에 초안 보드를 올린다(`design-canvas` 3절). 처음이면 새로 만든다. 사용자는 여기서 화면을 직접 고칠 수 있다.
   - `python -I scripts/build_kit.py <spec-kit>` → 플로우 맵(연결 · 기능정의 · 검토 이슈)도 게시한다.
   - Artifact가 없는 환경이면 진입 스킬의 "도구가 다를 때" 표대로(harness · 로컬 서버 · 파일).
6. **묻기**:

```
초안 화면 3개(F1 시설 목록 · F2 시설 등록 · B2 예약 상세)
  디자인 캔버스(직접 고칠 수 있음): <디자인 링크>
  플로우 맵(연결 · 기능정의 · 이슈): <플로우 맵 링크>
  자체 점검: 밀도 미달 0 · 휴리스틱 위반 5 → 고침 4 · 남김 1(H7 단축키, 개발 단계 결정)
아직 안 그린 화면: B1 예약 목록 · D1 대시보드
캔버스에서 고치시거나, 말로 주셔도 됩니다(일부만 답해도 됩니다):
  유지 — 좋은 점 / 수정 — 화면 ID + 무엇을 / 추가 — 빠진 항목 · 화면 / 질문
"좋아요"라고만 하면 이 방향으로 나머지 화면을 그립니다.
```

## 검토 · 개선 (반복)

1. **캔버스에서 고쳤으면 먼저 가져온다**:
   - 최신본 받기: `Artifact read`(url, paths: 바뀐 보드 · theme.css)로 내려받는다(저장 위치는 결과에 나온다).
   - `node scripts/import_design.mjs <받은 폴더> <spec-kit>` → 바뀐 보드 목록 확인 → `--apply`.
     - `design-import/<ID>.html`이 생기고 이후 빌드 · 내보내기에서 그 화면은 이 파일이 원본이 된다. 이후 그 화면을 고칠 때는 이 파일을 고친다.
     - "수동 반영 필요"(캔버스에서 컴포넌트 문법으로 바뀐 보드)는 보드를 읽고 시안에 옮긴다.
     - helmet에 추가된 스타일(`design-import/<ID>.css`)은 빌드에 함께 들어간다. 여러 화면에 쓸 값이면 theme.css · 토큰으로 옮긴다.
   - 캔버스 수정이 SB 마커 · 입력 필드 검수에 영향을 주는지 `check_docs.py` · 검수로 확인한다.
2. 말로 준 피드백은 표로 되묻지 말고 바로 분류해 반영한다: 화면(H · theme · 토큰) / 흐름(data-go · FLOWS) / 내용(문서 · 기능 ID) / 범위(요구 추가 · 삭제 → 근거노트도 갱신).
   - **아직 안 그린 화면에 대한 피드백**은 그 화면을 이번 회차에 새로 그려 반영한다.
   - **요구 목록에 없는 새 요구**는 추가하되 보고에 "범위 추가: … (기능 ID · 공수 영향 추정)"으로 따로 표시한다. 공수가 1인일 이상 늘면 반영 전에 한 줄로 확인한다.
   - 한 화면에서 고친 것이 다른 화면에도 해당하면(같은 컴포넌트 · 같은 패턴) 시안 도구 · 토큰 쪽을 고쳐 함께 바꾼다.
3. 해석이 두 갈래면 두 안을 캔버스에 나란히 올리거나(시안 비교와 같은 방식) 한 번만 묻는다.
4. 기록 — 의미 있는 변경은 `ISSUES`(`src: '검토 n회차'` 또는 `'캔버스 수정'`, `st: 'done'`)와 기능정의서 변경 이력에, 회차 요약은 `progress.md` 피드백 표에.
5. 다시 점검(4번) · 빌드 · 내보내기 · 게시하고 "n회차 반영: 캔버스 수정 2화면 · 말 피드백 수정 3 · 추가 1 · 보류 1(이유)"로 알린다. 캔버스 Artifact를 다시 게시할 때 사용자가 그 사이 또 고쳤으면 게시가 거절된다 — 최신본을 받아 다시 가져온 뒤 게시한다.
6. 회차가 3번을 넘거나 같은 곳을 되돌리면, 결정할 기준(예: "목록 우선 vs 지도 우선")을 짚고 선택을 받는다.

## 확장

- 남은 화면 목록과 순서를 보여 주고(메뉴 순 · 흐름 순) 바로 진행한다. 많으면 메뉴 단위로 나눠 보여 준다.
- 초안에서 정한 패턴 · 토큰 · 컴포넌트를 나머지 화면에 같게 쓴다. 다르게 해야 하면 이유를 적는다. 컴포넌트가 정리되면 `design-system/components.js`에 모아 캔버스 DS 보드로 보여 준다.
- 문서 3종의 나머지 절은 `spec-docs`, 연결 · 인스펙터 · 게시는 `flowmap-artifact`, 캔버스 다듬기는 `design-canvas`로 이어 간다.

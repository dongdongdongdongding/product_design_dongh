# 화면설계서(SB) 탭

`sb-pages.js` 한 파일에 쓴다. 엔진이 마커 위치 계산(글자 · 다른 원을 피해 자동 배치, 필요하면 지시선), 번호 ↔ 설명 강조, 들어오는 곳 · 나가는 곳 자동 표, 목차, 판정표 렌더링, 검수를 해 준다.

## 먼저: 참고 설계서 분석

사용자가 참고 SB를 주면 먼저 문법을 뽑아 `SBCONF.ref`(참고 분석 페이지)에 적는다. 볼 것: 머리줄 형식, 번호를 다는 순서, Description의 항목 순서, 하위 번호를 쓰는 경우, 예외를 본문 요약과 별도 상태표로 나누는 기준, 문구를 적는 방식(마침표까지), 화면 사이를 같은 상태값으로 잇는 방식, 참고 SB의 빈틈(화면 ID · 흐름도 · 이력 · 서버 실패 예외 누락 등). 분석 페이지는 `SBCONF.ref`에 `() => html`로 쓴다(references/mark-syntax.md). 참고가 없으면 엔진 기본 "작성 기준"이 나온다.

## 페이지 구성 (sb-pages.js 순서 = 쪽 번호)

1. `SBCONF = { cover, ref?, menus, menuNote, journeys, dict, swatches, mapIntro, mapNote, screenAlias, crossFeatures, fieldAliases, fieldPass, forbidden, forbiddenExempt, instructions, openItems }`
2. `pgDocs()` — 표지 · 작성 기준 · 메뉴/흐름 · 상태값 사전
3. 공통 화면 요소 페이지 1개(`common: true`) — 사이드바 · 머리줄 · 진행 표시 · 카드/입력 규칙
4. 메뉴 순서대로 화면 페이지, 필요하면 바로 뒤에 판정표 페이지(`kind: 'mx'`)
5. `pgMap(); pgVerify();` (안 부르면 맨 뒤에 자동). 나중에 화면을 추가할 때는 번호가 밀리지 않게 **맨 뒤에** 붙이고 목차는 메뉴 묶음으로 보여 준다

문법 세부(마커 위치 지정 · 설명 토큰 · 하위 상태 · 판정표)는 `references/mark-syntax.md`.

## Description 쓰는 법

번호마다 같은 순서로 쓴다: 구성 요소 → 입력 규칙(필수 · 자릿수 · 형식 · 기본값 · placeholder) → 동작(누르면 어디로 · 무엇이 바뀜) → `[예외]` 상황과 **화면 문구 그대로** → 데이터(`{저장}` 브라우저 · `{서버}` 기존 서버 · DB). 입력 필드는 상세명세 12.2와 같은 이름 · 규칙으로 쓴다. 예외 ID(`{EX-07}`)와 이어지는 화면(`{→P2}`)을 걸어 맥락을 잇는다.

- 같은 상태값은 모든 화면에서 같은 이름으로 쓰고, 상태값 사전(`dict.rows`)에 "정하는 곳 · 보이는 곳"을 적는다.
- 화면 사이에 값이 넘어가는 주요 흐름은 `journeys`로 그린다(노드 `{id, s, k:'save'|'srv'}`, 화살표 `{e: '넘어가는 값'}`).
- 조합 규칙(입력 상태 × 조건 → 버튼 상태 · 결과 문구)은 판정표 페이지로 뺀다.
- 사용자가 실제 개발 문서를 원하면 시연 · 예시 표기를 쓰지 않는다(`forbidden`이 검사한다).

## 마커가 어긋날 때

마커는 `q`(위치)로 요소를 찾는다. 시안 문구를 바꾸면 그 문구로 찾던 마커가 "대상 없음"이 된다 — 검수(`artifact-qa`)가 알려 준다. 문구 대신 클래스(`$.tabsx`)나 카드 제목(`^카드 제목`)으로 찾으면 덜 깨진다.

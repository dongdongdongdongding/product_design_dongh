# 기획 밀도 기준

"화면처럼 보이지만 기획이 비어 있는" 초안이 가장 흔한 실패다: 카드 세 개, 표 두 줄, 버튼 하나, 상태 · 규칙 · 예외 없음. 이 기준은 실무에서 개발 문서로 납품한 화면설계 산출물(화면 14개, 기능 34, 예외 59, 검수 21, 검토 이슈 16)을 잰 값의 **하한**이다.

## 화면 하나에 있어야 하는 것

| 항목 | 페이지 | 팝업 · 패널 · 상태 화면 | 왜 |
|---|---|---|---|
| 요소 수(`elems`, SVG 속 도형 제외) | 110+ | 100+ (뒤에 깐 화면 제외) | 실제 데이터 · 필터 · 상태 · 작업이 다 들어간 화면의 크기 |
| 보이는 글자(`chars`, 공백 제외) | 450+ | 250+ | 표 행 · 라벨 · 안내 · 상태 문구가 실제 업무 말로 차 있는가 |
| 구성(`parts`) | 4+ | 3+ | 머리 · 요약 · 목록/폼 · 보조 정보 · 작업 |
| 상태(`states`) | 2+ | 1+ | 빈 · 로딩 · 오류 · 권한 · 충돌 중 해당하는 것 |
| 규칙(`rules`) | 2+ | 1+ | 계산 기준 · 정렬 · 권한 · 입력 제한 |
| 예외(`ex`) | 2+ | 1+ | EX 문서와 연결 |
| 검수(`at`) | 1+ | 1+ | AT 문서와 연결 |

프로젝트 전체: 화면당 예외 평균 3개 이상, 검토 이슈가 화면 수의 절반 이상(원본 대비 해석 · 결정 · 미결), 공통 상태 화면 1개 이상(저장 실패 · 손상 · 빈 상태 · 권한 없음 예시).

재기: `node scripts/check_density.mjs <spec-kit>` — 화면별 숫자와 미달 항목, 종료 코드 1이면 미달.

## 숫자보다 먼저 볼 것

- **실제 데이터처럼**: 표는 6~10행, 값은 업무에 맞는 그럴듯한 값(이름 · 날짜 · 금액 · 상태가 섞여 있음). "항목 A · 항목 B" 금지. 개인 정보처럼 보이는 실명 · 연락처는 가상의 것으로.
- **모든 요구가 화면에 있음**: 요구 추적표 한 줄마다 "그 입력 · 동작이 어느 화면 어디에 있나"를 확인한다.
- **상태가 그려져 있음**: 목록 화면이면 필터 적용 표시 · 건수 · 정렬 · 페이지 · 선택 시 작업 바, 폼이면 필수 · 오류 · 저장 중 · 저장 완료.
- **결정이 남아 있음**: 원본이 모호한 곳은 기본안을 정해 그리고, 검토 이슈로 "왜 이렇게 정했나"를 남긴다.

## 하지 말 것

- 숫자를 맞추려고 의미 없는 요소 · 반복 행 · 장식 문구를 넣지 않는다. 미달이면 **빠진 기획**(상태 · 규칙 · 예외 · 보조 정보)을 찾는다.
- 기준은 하한이다. 사용자가 더 깊게 원하면 그쪽이 기준이다.

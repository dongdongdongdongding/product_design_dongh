# 개발 문서 3종

〔5/7 전체 확장〕 초안 단계(`draft-review`)에서 채운 뼈대를 이어서 채운다. 끝나면 `progress.md` 5단계 숫자를 갱신한다.

문서는 플로우 맵 · 화면설계서의 데이터 원본이다. `build_kit.py`가 **표 머리행 앞부분**으로 표를 찾으므로 머리행을 바꾸면 빌드가 멈춘다. 표 목록과 열 뜻은 `references/doc-tables.md`. 빈 틀은 `templates/project-starter/docs/`, 완성 예시는 `examples/demo-park/docs/`.

## 작성 순서

1. **기능정의서**: 변경 이력 → 범위 원칙(구현 구분 E 기존 / U UI / D 고정 데이터 / C 조건부 / F 후속) → 배포 기준선(실제 메뉴 · 옵션 · 확인 날짜) → 메뉴표(menuCode) → 5.1 화면 목록(SCR-xx) · 흐름도 → 5.2 요구 추적표 → 6장 기능 목록(6.1, 6.2 … 절마다 `| ID |` 표) → 기본 결정 표.
2. **상세명세**: 1.1 화면 표시 원칙 · 1.1a 디자인 기준(근거 노트의 측정값) · 1.1b 공통 화면 요소 → 데이터 계약 → 화면별 규칙 → 8장 예외 → 10장 검수 → 12장 입력값 · 서버 · DB → 13장 지도(지도가 있을 때).
3. **WBS**: `| WBS |` 표(괄호 인일은 조건부, 합계 제외) → 기준 합계 · 여유(×1.2~1.3) → 마일스톤 → 리스크.

화면 ID는 문서 · 플로우 맵 · 화면설계서 · 디자인 캔버스에서 같은 것을 쓴다(SCR-D1 ↔ D1).

## 원본과 대조

- 근거 노트의 요구 항목을 요구 추적표에 한 줄씩 옮기고, 항목마다 **그 입력 · 동작이 어느 화면 어디에 있는지**까지 확인한다. 기능 ID만 연결된 요구는 화면이 빠졌을 수 있다(예: "구역 범위" 입력 요구 → 구역을 그리고 고치는 화면 필요).
- 배포 사이트에서 확인한 사실로 문서의 가정을 고치고 날짜를 적는다. 고친 이유는 변경 이력 "근거" 열에 원본 위치로 적는다.

## 12장 입력값 · 서버 · DB

신규 기능마다 처리 위치(브라우저 / 기존 서버 / 신규 서버)와 운영 서버 · DB 영향을 한 줄로 쓴다. 12.2 입력 필드는 화면 ID · 키 · 타입 · 필수 · 검증 · 기본값 · 저장 위치를 모두 채운다 — 화면설계서 Description과 최종 검증("입력 필드가 화면에 있음")의 기준이다. 확인 못 한 서버 경로는 "배포 소스 확인 필요". 후속 API(12.4) · 테이블(12.5)은 제안이라고 쓴다.

## 13장 지도 표현 (지도가 있는 서비스)

기본 설정(SDK · 중심 · 레벨 · 범위 맞춤 · 컨테이너 100% · relayout) → 기호 표(지도 SDK 객체 · 색 · 선 · 쌓임 순서 · 상호작용) → 화면별 구성(기본 표시 · 토글 · 초기 범위 · 클릭 · 범례 · 실패) → 그리기 규칙. SDK가 못 그리는 표현(카카오 Polygon 무늬 채움 등)은 시안에도 쓰지 않는다.

## 확인 지점 (5단계 끝)

모든 화면 · 문서를 채우면 숫자(화면 · 기능 · 예외 · 검수 · WBS 합계)와 **사용자가 정할 것**(조건부 작업 포함 여부 · 공수 · 외부 확인)을 묶어 보여 준다. "이대로 화면설계서로 갈까요?" 다음 예고: "〔6/7 화면설계서〕".

## 검증

```
python -I scripts/check_docs.py --docs <docs> --screens D1,L1,...
python -I scripts/build_kit.py <프로젝트 폴더>          # kit.json expect 개수 검사 포함
```
